2. Mycelium Game Engine lives - What we've done so far.

June 4, 2025 · 3 min

Gameplan#

I needed a hook.

Why would I want to make a game on my engine? How is it different enough from Unreal or Unity to justify building a game on this, rather than one of those?

Truth is — it’ll never be fully justified. Those engines are simply too good. But I needed a hook regardless.

Entropy in Game Development as a first-class system#

I could be off — way off. I’ve never done this before, and I have no idea what I’m doing. But I don’t think Unity or Unreal treat time — or rather, change over time — as a first-class system.

They give you clocks, frame counters, deltas. But what about meaningful time?

I want to natively account for aging, decay, withering — systems that evolve without player input.

I want to start development with the idea that every single object in the game has a sense of how long it — and everything around it — has existed. Time should be treated the same as position or velocity: something every entity can feel, react to, and be changed by.

That’s why I’m calling my engine Mycelium — for its constant spreading, connectivity, and transformation. Like fungi.

If you’ve played Death Stranding, this probably sounds familiar — where footsteps wear paths into terrain and supernatural rain ages structures. This would enable that, but on a much grander scale where you have to opt-out of a path/building/flower aging.

ECS (Entity, Component, System)#

ECS (Entity, Component, System)

The first thing I built — after some light research into what a game engine actually is — was an ECS system.

Basically, it’s a relationship between:

Entities: objects/lights/noises/etc., represented only by a number

Components: basic data-only structs that represent an entity's properties

Systems: logic that runs on components

Why do this?

Because you can turn your entities into 64-bit bitsets where each bit represents the presence of a component. That lets your systems instantly query and operate only on the entities they care about — fast, cache-friendly, and decoupled.

I set up the basic structure in a few hours. It’s still pretty gnarly to wrap my head around — I’m used to object-oriented programming, and this is firmly data-oriented.

Rendering (SDL2, openGL)#

I’ve never rendered anything straight through a GPU-hitting API like this before, but I set up a Rendering System that currently just displays a triangle.

Turns out, after digging into graphics programming, a triangle is basically the “Hello World” of the GPU world.

I didn’t realize it, but the GPU is absurdly good at triangles. Everything — CGI, games, visual effects — is essentially triangles.

Also learned about fragments, which I think of as… weird quantum pixels? If you’ve got two triangles and one overlaps the other, the overlapped area only displays the closer triangle’s pixels. The would-be pixels from the triangle behind are still processed — these are fragments. That’s how I understand it so far.

Still learning.

Next Step:#

I need to integrate my Rendering System into the ECS.

That means building a component like Renderable, and having the rendering system query for entities that have both a Renderable and a Position component. It’ll pass that position to the GPU and — hopefully — I’ll be able to draw multiple triangles dynamically.

Essentially, I need to bridge the simulation layer with the rendering pipeline.

…if you wanted to be technical about it, like some kind of nerd.
